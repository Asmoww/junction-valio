# Decisions

One line each: date, decision, why. Don't reopen without a reason.

- 2026-11-13: Guardrails enforced in the gateway (policy engine), not only in the agent prompt. Why: judged on controls; a jailbroken agent must still be blocked.
- 2026-11-13: Quote-then-commit with quote expiry and idempotency keys. Why: fixed prices, no double orders on retry.
- 2026-11-13: Python 3.12+, FastAPI + Pydantic gateway, Anthropic SDK agent, MCP Python SDK, Jinja/htmx approval UI, SQLite, pytest, uv. Why: one language for the whole team, one process for the demo.
- 2026-11-13: Lookup verifies attributes from structured data (lactose 0 g/100 g, fat %), never from names alone; the shortlist keeps every qualifying product (no cut by name or file order). Why: the old cut dropped the €1.01 milk and overpaid €390 on the demo.
- 2026-11-13: Allergens: CONTAINS a banned allergen blocks; MAY_CONTAIN and missing data follow `allergen_policy` per mandate; missing data is "unknown", never "allergen-free". Why: 46 % of products have no allergen data.
- 2026-11-13: Every offer line carries signed trust flags (stock known?, cut-off, price basis, data gaps, reliability). Why: Valio's "trust protocol" question; agents can't verify claims otherwise.
- 2026-11-13: Unstated details (fat level, fresh vs long-life) are never guessed and never asked in a chat; the agent compares across them and shows the cost of each choice to the approver. Why: "not a chatbot"; one approval instead of two interruptions.
- 2026-11-13: Official substitutes must pass a fit check (same category). Why: Valio's own substitute for coffee milk is cream.
- 2026-11-13: Trap suite (`tests/traps`, `scripts/run_traps.py`) runs real-data cases against the live API; results shown in the Valio view. Why: proof, not claims. Mock quirks documented in `docs/ASSUMPTIONS.md`.
- 2026-11-13: Main repo is Asmoww/hackathon-1 again; `review/rasmus-context` stays a branch, never merged.
- 2026-11-13: Only a signed-in person can approve; an agent's Bearer token gets 403, and the approver must be in the mandate with authority for the total. Why: a hijacked agent must not sign off its own order.
- 2026-11-13: The price lock ends at the earliest of 15 min, any line's order deadline and any line's price validity; an approval after expiry re-checks the price and never places at a stale one. Why: "fixed price" has to stay true until the order is placed.
- 2026-11-13: Stock Valio can't confirm (supplier-warehouse "Terminal" products, or no availability answer) and lactose-free claims backed only by the product name need a person. Valio's own "Stock" products with a placeholder quantity count as confirmed and carry a trust flag (merge decision: otherwise nearly every live order needs a person). Why: the agent must not treat unknowns as facts.
- 2026-11-13: Order lines are validated before pricing (positive, whole units for pieces/boxes, lot size, no duplicates, max 20 lines). Why: a negative line could pull a large order under the auto-approve limit.
- 2026-11-13: Reality check on lookup: Claude sees the matching catalog categories (with sample names) and keeps only those that ARE the requested product, plainest form first (cream, not ice cream; beer, not beer-batter onion rings). It can only narrow results, never add products. No match at all → "not in Valio's catalog", stopped before any API call, with what does exist shown but never ordered. Why: keyword matching can't tell "is" from "contains"; the largest matching category was often the wrong product.
- 2026-11-13: Every dead end gets a specific answer and a next step, never a bare status: unit that doesn't fit the product (1,000 litres of chicken nuggets → sold by kg, "use 1,000 kg"), cheapest option above the hard limit (agent doesn't ask for an offer it knows will be blocked; offers the largest quantity within the limit), and "nothing can be ordered" broken down by reason (deadline passed, unavailable, no price). Suggestions only rewrite the request; nothing is ordered until the person runs it again.
- 2026-11-13: Claude model for request reading and the reality check: Sonnet 5.5 (was Opus 5.5). Why: 12/12 on the parsing comparison and the same category picks as Opus, at about half the cost; Claude only translates and narrows, the rules decide.
- 2026-11-13: One decision ladder decides every outcome (docs/FRAMEWORK.md, gateway/gates.py): Purchase? Clear? Possible? Allowed? Proven? Agent's call? The first "no" decides who acts next. Every policy rule maps to exactly one gate. Why: one MECE backbone that sorts any request and fits on one slide.
- 2026-11-13: Words in a request that the reading drops (extra products, brands) send it back to the requester instead of ordering part of it. Why: "chili cheese chicken … 100 litre milk" must not silently become a milk order.
- 2026-11-13: An unstated detail (fat %, fresh vs long-life) that moves the order by more than the mandate's tolerance (default €25) goes to the approver. Why: the UI promised the approver would see it; now it's true.
- 2026-11-13: Missing delivery history is allowed or needs a person, per mandate (`unknown_reliability`), and is always shown. Why: the mandate card and the rule contradicted each other.
- 2026-11-13: DEMO_CLOCK replays the mock's snapshot so fresh milk is orderable; labelled on every run and switchable off. Why: the snapshot's passed cut-offs forced 1 L UHT cartons at double the price.
- 2026-11-13: Instructions aimed at the agent inside a request ("ignore previous instructions…") stop the request at gate 1: nothing is followed, nothing is ordered, a security event is logged. Scanner checked against every supplier text in the product file: 0 false alarms. Why: a request says what to buy, never how the agent behaves.
- 2026-11-13: Split orders only combine products of the same kind (fat %, shelf life, lactose status). Why: a live run filled 1,000 L by mixing 3.5 % low-lactose, 1.5 %, fat-free and coffee milk.
- 2026-11-13: One order per signed offer; the requested quantity is sealed into the offer; unknown substitution types and unset mandate limits fail closed; late approvals recheck stock. Why: outside red-team review (ChatGPT) found ways around each.
- 2026-11-13: contracts/openapi.yaml: QuoteRequest gains optional `requested_quantity` (sealed into the offer); /v1/orders 409 covers a reused offer and a changed requested quantity. Additive, old clients still work.
- 2026-11-13: "200 eggs" counts eggs, not packs: pieces per pack read from the name (M10, 12 x, 40x90g, 100pcs); "200 cartons/packs" counts sales units. Unknown pack contents need a person ("Pack contents known", gate 4). Why: the agent ordered 2,000 eggs for €402.
- 2026-11-13: Buyer profile in each mandate (e.g. hotel milk: 1.5 %, fresh or long-life both fine) settles details a request leaves open. A preference, never a filter or an override, always shown. "Unstated details" only counts for dairy drinks (104xx). Why: 10 of 12 ordinary requests went to a person; now 5 of 12 are ordered alone, and the rest stop for real reasons (over limit, unconfirmed stock).
- 2026-11-13: Agent readiness in the Valio view, computed with the gateway's own rules on food products only (4,000 non-food items excluded): hotel 100 %, school 70 %, hospital 17 % of the catalog decidable alone, plus the categories to fix first. Why: our main insight belongs in the product, not in a doc. Corrected the earlier "46 % no allergen data" to 30 % of food.
- 2026-11-14: Agents and people have different secrets: `AGENT_TOKEN` (Bearer, default derived from DEMO_PASSWORD) vs DEMO_PASSWORD (sign-in). Why: with one secret an agent could sign in as a person and approve its own order (ChatGPT hostile review).
- 2026-11-14: A gate-4 approval records what the person checked; an empty or default comment is refused. Why: a click proves no fact.
- 2026-11-14: Pack size in /v1/quotes comes from Valio's prices (`requested_unit`), never from the caller's `perUnit`. Stock and cut-off are rechecked at commit. Additive in contracts/openapi.yaml.
- 2026-11-14: Framework rules 1 (loosens a control → instruction), 2 (assumed date → person confirms) and 6 (doubt is a no). Why: 155 of 1,000 "break it" prompts had no single exit under the old wording.
- 2026-11-14: Approve on your own phone: a signed-in person issues a QR for one pending order and one approver named in the mandate; the HMAC-signed link works once, for 30 minutes, without sign-in, and goes through the same approval rules. Agent tokens can't issue links. The Valio view lists waiting orders, so an outside agent's order can be approved there too.
- 2026-11-14: Agent vs. gateway scoreboard (scripts/scoreboard.py) reports what really happened: a strong model with the buyer's rules in its prompt behaves as well as the gateway on our 16 requests. So the claim is not "other agents fail"; it is that Valio can't choose which agents connect, and rules in the gateway hold for all of them. Extra columns run the same agent with the rules left out, on the raw API and through the gateway.
- 2026-11-14: Placed orders export as Peppol BIS Ordering 3 (UBL 2.1 Order), checked against the official UBL 2.1 XSD; not checked against the Peppol schematron, demo party identifiers. Why: buyers' ERPs already speak Peppol; no new format to adopt.
- 2026-11-14: Mandates are W3C Verifiable Credentials (vc+jwt, EdDSA) signed by the buyer, key published as did:web. The "Mandate valid" rule fails if the mandate differs from what the buyer signed. In the demo the gateway holds the buyers' keys and re-signs at startup; in production the buyer signs and the gateway holds only public keys.
- 2026-11-14: place_order (MCP and /v1/orders) accepts the offer_id as well as the JWS. Why: a live Claude Code agent mangled the long JWS when copying it; the gateway keeps the signed offer, so the id is enough and the signature is still checked.

- 2026-11-14 (Codex, requested by Rasmus; pending review): Add a shared read-only preplanner with explicit purchase/inquiry purpose in UI, /v1/preplan and MCP preplan_request. Inquiry in the built-in flow cannot order. Expose buyer hard rules separately from shared per-mandate agent authority, and disclose unsupported outside-agent/request-only limits. Additive contract proposal on feature branch; does not bind purpose or extra constraints into existing low-level quotes.
